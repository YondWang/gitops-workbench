# CI 子库独立编译与 MR 合入门禁计划

**日期：** 2026-10-09
**适用范围：** SimOS 主库、SimOS 当前子库（business、localization、mapengine、perception、pnc），以及后续纳入构建图的 config、costmap_node 等组件。  
**目标：** 所有 MR 在合入前完成规定编译验证；子库在各自项目中独立产出可复用包；SimOS 主库只消费固定版本的模块包，负责最后的组合、集成验证和系统包装配，不再重新编译子库源码。

## 1. 目标和完成定义

### 1.1 目标

1. 任一受保护分支的 MR 都必须有成功的 Required CI 状态才能合入。失败、取消、超时和未运行都不能被当作通过。
2. 每个子库拥有自己的 MR 编译流水线，使用固定构建镜像和目标架构，生成模块包、校验和及构建清单。
3. 子库构建输入通过版本化的 SimOS 基础 SDK/依赖包和明确的模块 SHA 固定，不再依赖 SimOS 工作区中的其他源码目录或上一次 Job 的 `build/install` 内容。
4. SimOS 集成流水线消费各子库的不可变包和 manifest，执行依赖安装、集成配置、集成测试、最终 resident/deb/镜像装配及发布。
5. 构建、测试、包发布、集成和正式发布互相分层；MR/分支验证不得上传正式云盘、OTA 或生产目录。

### 1.2 完成定义（DoD）

- 所有目标项目的 protected branch 已打开“成功流水线才能合并”规则，并明确 Required job 名称。
- 对每个子库创建一个真实 MR，能在 MR pipeline 中独立完成编译和最小安装/包校验；至少覆盖 `SIMBOT_R6_A`、`SIMBOT_R6_B` 两个配置，或有书面批准的矩阵裁剪规则。
- 任意 SimOS 集成 MR 可以只下载指定 SHA 的模块包，不执行子库源码编译；最终集成包内的模块清单与输入 manifest 一致。
- 任一模块构建失败、包缺失、SHA 不匹配、ABI/API 不兼容或集成测试失败，均能阻止合入/发布，并在 Job artifact 中留下可定位信息。
- 旧的“SimOS 一次流水线编译全部模块”路径被关闭或仅保留为明确标记的本地兼容入口，不能成为正式发布默认路径。

## 2. 当前 CI 基线

本计划约定 SimOS 主库在本项目中的目标路径为 `simos/`。截至本次扫描，当前工作区仍未出现该目录或 Git submodule；因此下面涉及 SimOS 脚本的现状结论，来自当前可访问的基线工程 `/home/simpleai/ubuntu2004/project/simos`。SimOS 目录纳入本项目后，应优先使用 `simos/.gitlab-ci.yml`、`simos/build_all_debs.sh` 等仓库内路径核对，外部路径只作为迁移前快照。

### 2.1 SimOS CI 触发和 Job 拓扑

- SimOS `simos/.gitlab-ci.yml` 的 workflow 只允许符合版本 Tag 的 API pipeline；Tag push 被显式禁用，其他来源全部 `when: never`。因此当前没有 MR pipeline，也没有 MR 编译门禁（`simos/.gitlab-ci.yml:1-7`）。
- 当前 stage 是 `package -> publish -> upload`（`simos/.gitlab-ci.yml:9-12`）。`resident_package` 和 `deb_package` 都只在 Tag 规则下运行，并分别按 `SIMBOT_R6_A/B` 做两个配置矩阵（`simos/.gitlab-ci.yml:41-86`）。
- `publish_nextcloud`、`publish_deb_nextcloud` 依赖整包构建 Job；OTA dev/test/prod Job 再依赖 deb 发布 Job（`simos/.gitlab-ci.yml:88-178`）。这意味着现有发布链路默认认为 SimOS Job 已经完成所有模块的编译。
- 构建镜像、Runner tag、Registry 上传开关和并行度目前写在 SimOS 主库变量中；deb 编译默认 `SIMOS_DEB_BUILD_MODE=all`、`SIMOS_DEB_BUILD_JOBS=16`（`simos/.gitlab-ci.yml:18-35`）。

### 2.2 `build_all_debs.sh` 和现行 deb Job

- `simos/ci/deb/ci-build-debs.sh` 负责 Git 鉴权、子模块 checkout、配置矩阵、交叉编译 pkg-config 和并行度限制，然后在每个配置变体中执行 `bash ./build_all_debs.sh`（`simos/ci/deb/ci-build-debs.sh:114-223`、`288-320`）。这说明现有脚本可以作为迁移的包装层和经验来源。
- `simos/build_all_debs.sh all` 先编译 SimOS 主包，再按固定顺序串行编译 business、localization、mapengine、perception、pnc（`simos/build_all_debs.sh:204-210`）。它最后还把所有 deb 汇总成 `resident_*.tar.gz`、`simos_*.zip` 和 `config.yaml`（`simos/build_all_debs.sh:235-255`）。因此它是“整套系统打包脚本”，不是独立子库编译器。
- 脚本提供 `simos`、`business`、`localization`、`mapengine`、`perception`、`pnc` 单目标入口（`simos/build_all_debs.sh:306-370`），可用于本地排查和迁移初期的单模块适配，但单目标入口仍没有独立的 workspace、依赖 SDK、manifest 和 Registry 发布契约。
- 当前 `simos/.gitmodules` 还列有 `src/config`、`src/costmap_node`；`simos/build_all_debs.sh` 的固定模块列表没有它们。这是构建覆盖范围与实际子模块定义不一致的已知缺口。

### 2.3 为什么当前“单目标”仍不等于独立编译

- 五个子库的 `simos/src/*/debian/rules` 都把 `PROJECT_ROOT` 指向 SimOS 根目录，并在根目录执行 `catkin_make install`；构建结果写入根目录共享的 `build/`、`devel/`、`install/`。
- 每个模块通过在其他模块下创建 `CATKIN_IGNORE` 来限制构建范围，然后再删除这些文件。这种方式适合一个 Job 内串行复用工作区，不适合多个并行 Job，也不满足“输入只来自本模块和已发布依赖”的可复现性要求。
- business、localization、mapengine、pnc 的 Debian 运行时依赖普遍声明 `simos`，并通过 `/work/share/project/resident` 和 `CMAKE_PREFIX_PATH` 使用主库安装内容；当前没有从 Package Registry 下载并校验 SimOS SDK 的步骤。perception 的依赖声明也与其他模块不一致，需要单独梳理。
- 模块 Job 若继续使用同一工作区，会产生 CMake cache、安装目录、权限和残留产物污染；若将多个模块 Job 并行化，则必须为每个 Job 提供独立 checkout/workspace 和独立输出目录。
- `build_all_debs.sh` 使用硬编码的模块目录、ROS Noetic 路径、ARM64 目标和 `sudo chmod 777`；这些假设需要在模块 CI 中被显式化、收敛或移除。

## 3. `build_all_debs.sh` 的复用结论

### 3.1 可以复用的部分

1. `dpkg-buildpackage -us -uc -b`、deb 输出文件筛选、版本命名和现有 Debian 元数据，可作为第一阶段的兼容实现。
2. `ci/deb/ci-build-debs.sh` 中的 Git URL rewrite、私有子模块鉴权、配置矩阵解析、交叉 pkg-config、并行度限制和失败元信息生成，可抽取为共享 CI 模板或脚本库。
3. `build_all_debs.sh business` 等单模块入口，可先用于验证某个模块的依赖闭包和包内容，帮助建立迁移前后的产物基线。

### 3.2 不应直接复用的部分

1. 不应在每个子库 MR 中调用 `build_all_debs.sh all`；这会重复编译所有模块，并继续把 SimOS 当成唯一编译入口。
2. 不应把 `build_all_debs.sh <module>` 直接当成最终独立 Job；它仍依赖 SimOS 根目录工作区、共享安装前缀和 CATKIN_IGNORE 副作用。
3. 不应在模块 CI 中生成整套 `resident_*.tar.gz`/`simos_*.zip`，也不应在 MR pipeline 中执行 Nextcloud、OTA 或生产发布。
4. 不应以“固定五个目录”作为构建图的唯一来源；模块清单、包名、依赖、配置和发布规则应由版本化 manifest/CI 模板显式声明。

### 3.3 推荐改造方式

将脚本演进为两层：

```text
共享构建库
  ├─ checkout/auth/toolchain/config matrix
  ├─ build_one_deb(module, source, sdk, output)
  ├─ write_manifest/checksum/SBOM
  └─ publish_immutable_artifact

各子库 CI
  └─ 调用 build_one_deb，仅编译本子库并发布 module artifact

SimOS 集成 CI
  ├─ 下载并校验所有 module artifact
  ├─ 安装到隔离的 integration rootfs/workspace
  ├─ 编译/装配 SimOS 主库和最终系统包
  └─ 运行集成测试及后续发布
```

第一阶段可以保留 `build_all_debs.sh` 作为本地兼容入口；正式 CI 应逐步改为 `build_one_deb.sh` 或等价的共享模板。迁移过程中应保留同一输入版本做新旧结果比对，确认包文件、安装路径和运行时依赖没有无意变化。

## 4. 目标架构和流水线契约

### 4.1 目标构建图

```text
子库 MR
  └─ module:compile/test/package
       └─ module artifact + manifest（绑定 MR SHA）

SimOS MR 或集成候选
  └─ resolve manifest（每个模块固定 SHA/包版本）
       └─ download/verify/install module artifacts
            └─ SimOS base/integration build
                 └─ integration test
                      └─ final resident/deb/镜像 artifact
                           └─ 受控发布（仅 Tag/批准流水线）
```

### 4.2 模块 artifact 最低契约

每个模块至少发布以下内容，文件名和包版本必须可由模块 SHA 唯一确定：

| 字段 | 要求 |
| --- | --- |
| `module` | 稳定的模块 ID，如 `business` |
| `source_sha` | MR pipeline 的精确 commit SHA，禁止只用可变分支名 |
| `package_name/version/arch` | Debian 包名、版本、目标架构 |
| `config_ref/config_sha` | 配置矩阵选择及其精确 commit |
| `simos_sdk_version` | 编译所用基础 SDK 版本和 SHA |
| `build_image_digest` | 构建镜像 digest，不只记录 mutable tag |
| `dependencies` | 直接依赖及其版本/ABI 约束 |
| `files` | 文件名、大小、MD5、SHA-256 |
| `tests` | 编译、单元、安装 smoke test 结果 |
| `created_by` | pipeline/job/project URL、时间、不可变 Registry 路径 |

模块包、manifest、SBOM（至少 SPDX 或 CycloneDX 之一）和日志摘要应一并上传。正式发布只能消费已验证且不可变的 manifest。

### 4.3 SimOS 集成契约

- SimOS MR 必须提交或生成一个 integration manifest，列出每个模块的项目、SHA、artifact URL、包校验和、配置变体和 SDK 版本。
- 集成 Job 不根据模块分支头重新解析版本，不使用“最新成功包”；所有下载均按 SHA/版本和校验和定位。
- SimOS 只编译自身仍归属主库的基础/集成代码，并负责安装模块包、生成最终 resident/deb/镜像和执行跨模块测试。
- 发布 Job 只能 `needs` 成功的 integration Job，不能直接依赖任意单个模块 Job。MR pipeline 和正式 Tag pipeline 使用不同的 Registry namespace/channel。

## 5. MR 合入门禁设计

### 5.1 必须落地的 GitLab 设置

1. 每个子库和 SimOS 主库的受保护目标分支启用“成功流水线才能合并”。
2. 将 `module:compile`、必要的 `module:package-smoke` 和 SimOS 的 `integration:test` 标为 Required；禁止通过手工跳过、允许失败或不存在 Job 绕过门禁。
3. 启用 merged results 或等价的 merge train 策略，避免 MR pipeline 只验证旧的 source branch、合并时却面对已变化的目标分支。
4. 统一 Runner tag、镜像 digest、超时、重试和资源限制；编译 Runner 不应挂载 Docker socket 或生产发布凭据。
5. MR pipeline 只保存小型元信息和测试报告，大包进入按项目隔离的 MR/candidate Registry；设置清理策略，禁止污染正式包名。

### 5.2 pipeline rules 建议

每个子库的 CI 至少区分以下来源：

- `merge_request_event`：编译、单元测试、包构建、安装 smoke test；不发布正式云盘/OTA。
- `push` 到受保护分支：可执行合并后验证和缓存预热，但不能取代 MR Required job。
- `pipeline`/`trigger`：由 SimOS 集成流水线按精确 SHA 触发；需要回传完整 job 状态。
- `tag`/受控 `api`：仅在集成通过、审批和版本清单冻结后进行正式发布。

当前 SimOS 的 Tag-only workflow 不能直接扩展成 MR 门禁；应新增明确的 MR 分支并保留发布规则隔离，避免 MR pipeline 误触发 Nextcloud/OTA。

### 5.3 跨仓库 MR 的状态传播

- 子库 MR：子库自身 Required compile 必须通过；若变更了公共 API、消息、ABI 或包契约，触发对应的 SimOS integration pipeline。
- SimOS MR：根据 integration manifest 触发或下载所有依赖模块的成功 artifact；任何缺失或不兼容都失败。
- 需要“子库 MR 合入前就验证 SimOS”的模块，采用 multi-project pipeline/trigger strategy，并通过 API/Bridge 将下游 integration 状态回传到上游 MR。状态回传必须绑定 source SHA，防止旧 pipeline 覆盖新提交。
- 第一阶段可先将跨仓库集成作为 `required` 的 SimOS 侧 pipeline；在 GitLab 权限和状态回传验证前，不允许把“子库单独通过”误认为“系统集成通过”。

## 6. 分阶段实施计划

### 6.0 阶段总览和优先级

| 阶段 | 优先级 | 主要目的 | 是否改变正式发布路径 | 完成标志 |
| --- | --- | --- | --- | --- |
| 阶段 0 | P0 | 盘点依赖、冻结契约、保存旧链路基线 | 否 | 所有模块和边界有明确结论 |
| 阶段 1 | P0 | 先让 MR 编译结果成为合入门禁 | 否 | 失败 MR 无法合入 |
| 阶段 2 | P1 | 选一个模块完成真正独立编译试点 | 否，双轨运行 | 模块可脱离整套源码构建并产包 |
| 阶段 3 | P1 | 解决主库/子库联合修改，建立跨项目集成 | 仅 candidate | 固定 SHA 对能完成联合验证 |
| 阶段 4 | P1 | 全部模块迁移到 artifact 集成 | 切换 candidate | SimOS 不再重新编译模块源码 |
| 阶段 5 | P0 | 正式发布切换、旧链路下线、回滚 | 是 | 正式发布只消费已批准 manifest |
| 阶段 6 | P2 | 指标、故障注入和新增模块治理 | 否 | 构建和发布可持续运营 |

阶段 1 必须早于阶段 2 完成：即使独立编译还未完成，也要先保证 MR 有编译门禁。阶段 2 至阶段 4 必须双轨运行，至少保留一段时间的旧整包构建作为结果对比和回退依据。

### 阶段 0：盘点、基线和决策冻结（P0）

**目标：** 在改 CI 前把“谁编译什么、依赖什么、产出什么、谁负责”固定下来，避免迁移过程中反复争论边界。

#### 步骤 0.1：建立模块清单

以 `simos/.gitmodules`、`simos/build_all_debs.sh`、各模块 `debian/control` 和 `debian/rules` 为输入，建立一份版本化清单，至少包含：

| 项目 | 当前模块 |
| --- | --- |
| 独立 deb 候选 | business、localization、mapengine、perception、pnc |
| 集成资源候选 | config、costmap_node |
| 主库基础/装配 | simos 根目录、common、driver、tools 等非模块目录 |

对 `config`、`costmap_node` 必须做出明确选择：是独立发布包、随主库集成的源码，还是仅在特定配置下使用。未做选择前，不得把它们默认为“已完成独立编译”。

#### 步骤 0.2：记录旧链路基线

在一个固定 Tag/SHA 和固定配置矩阵上运行现有 `simos/ci/deb/ci-build-debs.sh`，保存：

1. `build_all_debs.sh all` 的完整日志和返回码；
2. `deb_packages/` 中所有 deb、`resident_*.tar.gz`、`simos_*.zip`、`config.yaml`；
3. 每个子模块 SHA、配置 SHA、构建镜像 tag/digest、Runner 类型；
4. 每个阶段耗时、峰值内存、峰值磁盘和最终产物 SHA-256；
5. 安装到干净 rootfs 后的包列表和最小启动结果。

该基线用于后续新旧结果比对，不能只保留“流水线成功”这一状态。

#### 步骤 0.3：冻结构建边界

必须形成书面结论：

- SimOS 最终集成是否需要单独版本化的 base SDK；如需要，明确 SDK 的生产/维护 pipeline 和版本策略，不能把它隐式塞回每个模块编译 Job 或每次最终装配；
- 哪些内容由子库 deb 完整提供；
- 模块之间是否允许源码级依赖，还是只能通过 SDK/deb 依赖；
- `/work/share/project/resident` 中哪些文件属于 SDK，哪些文件只能在最终装配阶段生成；
- 两个配置矩阵是否都适用于所有模块。

#### 步骤 0.4：盘点 GitLab 权限和资源

逐项验证：

- 子库项目是否允许 `merge_request_event` pipeline；
- SimOS 是否能用 Job Token 下载子库 candidate artifact；
- 子库能否触发 SimOS multi-project pipeline；
- pipeline 状态能否回写到源 MR 的精确 SHA；
- Generic Package Registry 是否支持按项目、SHA、channel 隔离；
- 编译 Runner 是否有足够 ARM 交叉工具链、ROS Noetic、sysroot、内存和磁盘；
- protected variables 是否会被 MR pipeline 错误暴露。

#### 阶段 0 产出和验收

产出以下文件或 GitLab 配置记录：模块清单、依赖图、artifact 契约、旧链路基线报告、权限矩阵、Runner 容量表、责任人列表。

**不得进入阶段 1 的条件：** 某模块没有 owner、构建输入不明、包名不明、或正式发布凭据仍可被普通 MR Job 使用。

### 阶段 1：建立 MR 编译门禁（P0，不改变正式发布架构）

**目标：** 先实现“没有成功编译就不能合入”，暂时允许内部仍使用旧整包脚本，但必须隔离正式发布。

#### 步骤 1.1：统一 Job 名称和规则

各子库至少提供以下固定 Job：

```text
module:validate
module:compile
module:package-smoke
```

SimOS 主库至少提供：

```text
simos:validate
simos:integration-smoke
```

在 `merge_request_event` 下运行编译和 smoke test；在 Tag/API 下保留当前正式发布规则。MR 规则不得通过 `when: manual`、`allow_failure: true` 或“没有匹配规则时跳过”绕过 Required job。

#### 步骤 1.2：先做过渡版 Job

过渡版可以复用：

- `simos/ci/deb/ci-build-debs.sh` 的鉴权、配置矩阵、交叉 pkg-config 和失败 artifact 逻辑；
- `simos/build_all_debs.sh <module>` 的单模块入口；
- 当前 `SIMOS_DEB_BUILD_IMAGE`、`SIMOS_DEB_BUILD_JOBS` 和 Runner tag。

子库的 MR 代码不能只在子库仓库里裸跑 `dpkg-buildpackage`，因为当前 `debian/rules` 实际需要 SimOS 工作区。过渡期建议由子库 MR pipeline 发起一个绑定 commit SHA 的构建：

1. 子库 MR pipeline 读取自己的 `CI_PROJECT_ID`、`CI_MERGE_REQUEST_IID`、`CI_COMMIT_SHA`，触发 SimOS 的受信任构建入口；
2. 构建入口按固定 SimOS base/SDK SHA 创建全新 workspace，并按该 SimOS commit 的 gitlink checkout 全部依赖；
3. 在执行现有 `prepare_submodules` 后，把被测模块目录替换为子库 MR 的精确 `CI_COMMIT_SHA` 内容。推荐增加显式的 `SIMOS_MODULE_PROJECT_ID`/`SIMOS_MODULE_PATH`/`SIMOS_MODULE_SHA` override hook，并在日志、manifest 中记录；不能用分支名或 `--remote`；
4. 调用 `build_all_debs.sh <module>` 做过渡编译/打包；如果现有包装脚本无法安全支持 override，先写一个很薄的 MR wrapper，不要直接改动正式 Tag 构建默认路径；
5. 下游构建结果通过该 GitLab 版本支持的 downstream pipeline status propagation（如 trigger job 的 `strategy: depend`/`mirror`）回传给源子库 MR，使 MR Required pipeline 等待实际下游构建完成。

此方案仍然是“在 SimOS workspace 中验证子库 MR”，不是最终独立编译；但能在独立构建改造完成前先建立真实的 MR 编译门禁。

但必须增加以下隔离：

- 每个 Job 使用全新 checkout 和独立的 `CI_PROJECT_DIR`；
- `SIMOS_DEB_PACKAGE_REGISTRY_NAME` 改为 MR/candidate namespace；
- MR Job 不执行 `publish-debs-from-gitlab-package.sh` 的正式发布路径；
- 禁止访问 Nextcloud、OTA 和生产目录；
- 输出必须带 `project_id/source_sha/pipeline_id/config_sha`。

#### 步骤 1.3：配置分支保护

先在一个试点项目启用“成功流水线才能合并”，验证以下行为后再推广：

1. 编译失败的 MR 显示不可合入；
2. Job 取消、超时、未创建都不能被视为成功；
3. 新 commit 会使旧 pipeline 状态失效；
4. 重试旧 Job 不会覆盖新 SHA 的状态；
5. 只有明确的 Maintainer/Release Manager 角色可以执行紧急绕过，并留下审计记录。

#### 阶段 1 产出和验收

产出：各项目 MR CI 模板、分支保护配置、Job 命名规范、MR candidate artifact 规则、失败诊断模板。

**验收：** 每个试点项目至少验证一个成功 MR、一个编译失败 MR、一个超时/取消 MR、一个新 commit 替换旧 commit 的 MR。全部通过后才可把门禁设为正式 Required。

### 阶段 2：模块独立构建试点（P1，双轨运行）

**目标：** 证明一个模块能够只依赖明确的 SDK/deb 输入，在独立 workspace 中构建，不再依赖 SimOS 根目录的共享 `build/devel/install`。

**试点顺序：** 建议 `localization` 或 `mapengine` → `business` → `perception` → `pnc`。选择时以实际依赖和资源测量为准，不以目录大小作为唯一标准。

#### 步骤 2.1：抽取共享构建函数

从 `simos/ci/deb/ci-build-debs.sh` 抽取为可被各项目 include 的共享脚本或 CI component：

- `configure_git_auth`：保留现有 URL rewrite 和私有仓库访问方式；
- `checkout_config_ref`：复用 `simos/ci/common/checkout-config-ref.sh`；
- `configure_cross_pkg_config`：保留 sysroot 和 pkg-config 处理；
- `cap_deb_parallelism`：保留 `SIMOS_DEB_BUILD_JOBS` 校验；
- `write_manifest`：新增模块、SHA、SDK、镜像 digest、文件校验和；
- `publish_candidate_artifact`：按精确 SHA 写入 candidate Registry。

不要复制多份脚本；优先在 `simos/ci/common/` 增加共享实现，再让各子库 CI 调用。

#### 步骤 2.2：定义并生成 SimOS base SDK

先由 SimOS 主库生成版本化 SDK，至少包含：

- ROS Noetic 和编译器/交叉工具链信息；
- 主库基础包和公共消息的 headers、libraries、CMake/pkg-config metadata；
- 模块编译需要的 `/work/share/project/resident` 基础内容；
- target architecture、config ref/config SHA、SDK ABI 版本；
- SDK manifest、SBOM 和 SHA-256。

SDK 发布到 candidate Registry，版本不能只使用 `latest`。正式 SDK 由受保护 Tag 生成；MR SDK 使用 `mr-<iid>-<sha>` 等不可变命名。

#### 步骤 2.3：改造试点模块的 Debian 构建

按以下顺序改造试点模块的 `debian/rules`：

1. 将 `PROJECT_ROOT := $(CURDIR)/../..` 改为模块自己的 workspace 或由 CI 传入的显式路径；
2. 用 `SIMOS_SDK_ROOT`/`CMAKE_PREFIX_PATH` 指向下载并校验的 SDK；
3. 删除通过给其他模块创建 `CATKIN_IGNORE` 来控制构建的逻辑；
4. 禁止读取同一 Runner 上一次 Job 留下的 `build/`、`devel/`、`install/`；
5. 将依赖写入 `Build-Depends`、`Depends` 和 manifest；
6. 保留原 deb 包名和安装路径，避免一次迁移同时改变包接口；
7. 将 `sudo chmod 777` 改为 Job workspace 内的明确权限设置。

如果模块当前必须使用主库源码才能编译，先不要宣称“独立构建完成”，应把该依赖转化为 SDK 内容或列为阶段 2 未完成项。

#### 步骤 2.4：执行新旧双轨比对

同一模块 SHA、同一配置、同一镜像 digest 下同时执行：

- 旧路径：隔离工作区中的 `build_all_debs.sh <module>`；
- 新路径：模块 CI 的 `module:compile/package-smoke`。

比较：包名/版本/架构、文件列表、安装路径、依赖、ABI、导出符号、启动 smoke test、产物校验和、耗时、内存和磁盘。差异必须分类为“预期差异”或“阻断差异”，不能只比较 Job 是否成功。

#### 阶段 2 退出条件

- 删除其他模块源码后，试点模块仍能成功构建；
- 同一输入在两次独立 Runner 上产出相同或经批准可解释的校验和；
- artifact manifest 可被 SimOS 集成 Job 下载和校验；
- 旧路径和新路径的包内容差异已经评审；
- 试点模块 MR Required job 连续通过至少 3 次真实 MR。

### 阶段 3：主库与子库同时修改的联合构建（P0/P1，必须单独设计）

**核心原则：** 任何时候都不能把“主库目标分支最新版本 + 子库 MR 最新版本”这种隐式组合当作验证输入。联合构建必须由一份不可变的 **Integration Candidate** 明确记录所有参与仓库的精确 SHA。

#### 3.1 先区分三种修改类型

| 类型 | 例子 | 推荐验证方式 | 合入顺序 |
| --- | --- | --- | --- |
| 仅子库内部修改 | 算法、实现、配置不改变接口 | 子库 MR 编译；必要时用当前稳定 SDK 做集成 | 子库先合入 |
| 子库修改依赖主库已有能力 | 使用已发布的新 header/library/API | 子库 MR 直接消费最新稳定 SDK；SimOS 只做回归 | 先确认主库能力已在目标分支 |
| 主库和子库同时改契约 | 新消息、API、ABI、安装路径或包依赖 | 主库候选 SHA + 子库候选 SHA 的联合集成流水线 | 联合验证后按依赖顺序合入 |

不能因为子库单独编译成功，就认为第三类修改可以合入。第三类必须执行联合构建。

#### 3.2 Integration Candidate 的最小数据

联合流水线开始时生成 `integration-manifest.json`，至少包含：

```json
{
  "candidate_id": "ic-<timestamp>-<sha>",
  "simos": {
    "project_id": "<id>",
    "source_sha": "<simos-mr-head-sha>",
    "ref": "refs/merge-requests/<iid>/merge"
  },
  "modules": [
    {
      "project_id": "<module-id>",
      "source_sha": "<module-mr-head-sha>",
      "mr_iid": "<iid>",
      "artifact_pipeline_id": "<id>",
      "artifact_digest": "sha256:<digest>"
    }
  ],
  "sdk": {
    "source_sha": "<simos-sdk-sha>",
    "artifact_digest": "sha256:<digest>"
  }
}
```

`candidate_id` 只是检索名，真正的信任依据是每个项目的 `source_sha`、artifact digest 和 manifest 签名/校验和。

#### 3.3 推荐的触发流程

1. 子库 MR pipeline 在 `CI_COMMIT_SHA` 上执行 `module:compile`，产出绑定该 SHA 的 candidate deb、manifest 和 SBOM。
2. 如果子库变更影响公共 API、ABI、消息或包契约，子库 pipeline 触发 SimOS 的 multi-project integration pipeline；传入 `MODULE_PROJECT_ID`、`MODULE_MR_IID`、`MODULE_SHA` 和 candidate artifact 地址。
3. SimOS 集成 pipeline 不使用主库分支头，而是使用 SimOS MR 的 merge ref（如 `refs/merge-requests/<iid>/merge`）或明确的 SimOS MR HEAD SHA。
4. 集成 Job 下载子库 candidate artifact，校验 `source_sha`、包名、配置 SHA、SDK 版本和 digest；任何一项不一致立即失败。
5. 集成 Job 按 manifest 安装模块包，只编译 SimOS 主库剩余的基础/装配部分，然后运行集成测试。
6. pipeline 完成后，将结果回写到**发起本次候选的子库 MR SHA**以及 SimOS MR SHA。状态描述中必须显示 `candidate_id` 和完整 SHA 对。
7. 任一 MR 新提交后，旧 candidate 自动标记为 stale；旧 pipeline 即使随后成功，也不能更新新 SHA 的 Required 状态。

#### 3.4 子库 MR 依赖主库 MR 的情况

如果子库代码必须使用主库 MR 中尚未合入的新 SDK/API：

1. SimOS MR 先构建一个临时 SDK candidate，命名与 SimOS MR SHA 绑定，例如 `simos-sdk:mr-<iid>-<simos-sha>`；该 SDK 只进入 candidate Registry。
2. 子库 MR pipeline 通过显式变量 `SIMOS_SDK_PROJECT_ID`、`SIMOS_SDK_SOURCE_SHA`、`SIMOS_SDK_ARTIFACT_DIGEST` 下载该 SDK，不能从 `latest` 或主库分支名推导。
3. 子库构建成功后生成子库 candidate artifact；SimOS 联合 pipeline 同时消费 SimOS MR SHA 和子库 MR SHA。
4. 如果主库 MR 的集成代码又依赖该子库新包，必须由同一个 Integration Candidate 同时锁定两边，禁止拆成两个独立“先成功再猜测兼容”的 pipeline。

这套方式解决了“子库依赖主库、主库同时依赖子库产物”的闭环问题：主库 MR 提供临时 SDK，子库 MR 提供临时模块包，集成流水线验证两者的精确组合。

#### 3.5 合入顺序和冲突策略

**情况 A：接口向后兼容。**

- 先合入子库 MR 或主库 MR 均可，但合入前必须让目标分支重新跑一次对应集成验证；
- 子库 MR 合入后，SimOS MR 需要 rebase 到新的目标分支并更新 gitlink/manifest；
- 旧的联合 pipeline 不得直接作为 rebase 后 MR 的通过结果。

**情况 B：主库先提供兼容能力，子库后切换。**

- 主库 MR 先实现向后兼容 API/消息/包能力，并通过主库自身集成测试；
- 主库合入后生成正式 SDK candidate/stable SDK；
- 子库 MR 基于该 SDK 构建并合入；
- 最后再清理主库中的旧兼容路径，清理动作必须另起 MR 并重新走完整门禁。

**情况 C：子库先提供兼容包，主库后切换。**

- 子库先发布同时兼容旧主库的包；
- 子库 MR 合入并生成稳定 artifact；
- SimOS MR 更新 gitlink/manifest，集成测试通过后合入；
- 不能先删除旧接口再等待主库切换。

**情况 D：双方必须同时改变，无法向后兼容。**

- 建立一对关联 MR 和一个 Integration Candidate；
- 两个 MR 都只能以联合集成状态作为 Required 条件，单仓库编译通过不够；
- **不要把“两个 MR 几乎同时点合并”当成原子合入。** GitLab 的两个不同项目没有跨项目事务；第一边合入到第二边合入之间，目标分支可能处于不兼容状态，且第二个 MR 的 merge ref 可能已经过期。
- 首选将破坏性变更拆成三步：主库先发布同时支持旧/新接口的兼容版本；子库切换到新接口并合入；最后主库另一个 MR 删除旧接口。每一步都保持主干可编译。
- 若确实无法拆分，使用一个受保护的跨项目 release/integration freeze 窗口：暂停相关项目的其他合入；先合入基础 API/SDK 一方；立即更新另一 MR 的目标分支、重建 candidate 并确认 required integration 成功；再合入另一方；最后在两个项目的目标分支分别运行验证。任何一步失败就停止后续合入并按预先写好的兼容修复或 revert 方案恢复。
- 这个 freeze 方案只能缩短不兼容窗口，不能提供真正原子性。若业务不能接受任意短暂的不兼容状态，则必须拆成向后兼容的分阶段发布，不能采用跨仓库连续合入方案。
- 合入第二个 MR 后必须再跑一次目标分支 pipeline，验证真实合入结果，而不是只依赖合入前的临时组合。

#### 3.6 防止“旧结果误放行”的控制点

- GitLab pipeline/job 的状态天然绑定到某个 commit；下游回传给 MR 的状态必须挂在本次触发的子库 SHA 上。状态描述/manifest 要显示主库 SHA、子库 SHA 和 candidate ID，不能把旧 candidate 的成功当成新 commit 的成功；
- 对 GitLab 配置的 Required job 名称应保持稳定，避免动态 job name 导致保护规则匹配不到；动态 candidate 标识放在状态描述和 artifact manifest 中；
- 回写状态前，集成 Job 必须再次调用 GitLab API 检查源 MR 的当前 HEAD SHA；
- manifest 中的 SHA、artifact digest、SDK SHA 三者必须互相引用；
- artifact 下载后再次计算 SHA-256，并验证 manifest 中的包名、版本、架构和配置；
- MR rebase、force-push、关闭/重开或目标分支变化时，自动将旧 candidate 标记为 stale；
- merge train 中每个 train position 使用自己的 Integration Candidate，不能复用普通 branch pipeline 的结果。
- 不要把子库 MR pipeline 的成功状态直接复用为 SimOS MR 的集成成功状态；两者的 required status 分开，关联同一 candidate ID。

#### 阶段 3 产出和验收

产出：跨项目 pipeline 模板、`integration-manifest.json` 生成器、candidate Registry 约定、状态回写脚本、联合 MR 操作手册。

**验收场景：**

1. 只改子库：子库编译通过，SimOS 使用稳定 SDK 集成通过；
2. 只改主库：SimOS 自身集成通过，未变更模块使用稳定 artifact；
3. 主库和子库同时改：使用两个 MR SHA 的 candidate 集成通过；
4. 子库 MR 新提交：旧集成结果不能让新 commit 合入；
5. artifact digest 被替换：集成在安装前失败；
6. 其中一条 MR 关闭或 rebase：candidate 失效，必须重新生成；
7. 两个 MR 联合验证通过后，先合入其中一方并更新另一方的目标分支：旧联合状态必须变为 stale，另一 MR 必须重新构建；不能沿用前一个 SHA 对的通过结果；
8. 模拟第二个 MR 构建失败或 merge ref 变化：停止合入并按约定恢复，不允许把失败的另一半留在目标分支后继续发版。

#### 3.7 处理“主库必须先提供构建依赖”的可操作策略

如果每个子库都需要 SimOS 主库生成的公共头文件、消息、库或安装空间，不能把“SimOS 主库完整源码”直接作为每个模块 Job 的任意可变输入。按下面优先级处理：

1. **稳定公共依赖优先产品化：** 将模块共同需要的内容做成 SimOS Base SDK/deb。主库提交后生成版本化 SDK；子库只消费明确的 SDK 版本、SHA 和 digest。
2. **公共接口变更先向后兼容：** 主库先加新 API/消息，同时保留旧接口；生成新 SDK 后，子库可以逐个迁移。等所有消费者已迁移，再单独删除旧接口。
3. **确实要联合开发时使用 MR SDK candidate：** SimOS MR 产出只绑定主库 MR SHA 的临时 SDK，子库 MR 显式选择它，双方再由 Integration Candidate 锁定组合验证。
4. **禁止隐式依赖默认分支：** 子库 Job 不得在构建时 `git clone main`、`git submodule update --remote` 或下载 `latest` 来补齐主库依赖。必须从 manifest 指定的 commit/artifact 获取。
5. **SDK 不是最终集成结果：** SDK 只解决编译期公共依赖；最终 SimOS integration pipeline 仍需安装所有模块 candidate 包并跑端到端集成测试。

每个子库的 `debian/control` 与 manifest 应注明依赖的 SDK ABI/API 范围。主库若做不兼容变更，CI 应根据依赖清单找出所有消费者，并要求相关子库 MR 或明确的兼容性证明；不能只靠开发者记忆判断影响面。

### 阶段 4：全部子库迁移和集成流水线（P1）

**目标：** 将阶段 2 的独立编译模式推广到所有确认属于模块的项目，SimOS 只消费 artifact。

#### 步骤 4.1：按模块逐个切换

每个模块完成以下固定顺序后，才能从旧链路切换：

1. 子库 MR Job 能独立编译和产包；
2. candidate artifact 能被 SimOS 下载和校验；
3. 主库/子库同时修改的联合场景已通过；
4. 与旧整包输出完成差异比对；
5. 至少 3 次普通 MR 和 1 次失败恢复演练通过；
6. 模块 owner、回滚 artifact 和弃用旧入口已登记。

建议先切 localization/mapengine，再切 business，最后切 perception/pnc；每切一个模块都保留旧脚本的该模块入口，不要一次性删除全部兼容逻辑。

#### 步骤 4.2：改造 SimOS 集成流水线

新增或重构为以下 stage：

```text
resolve-manifest
  -> download-module-artifacts
  -> verify-artifacts
  -> install-module-artifacts
  -> build-simos-integration
  -> integration-test
  -> assemble-final-package
  -> publish
```

具体要求：

- `resolve-manifest` 只接受显式 SHA、artifact digest 和配置矩阵；
- `verify-artifacts` 必须在安装前完成；
- `build-simos-integration` 只做模块包安装、系统配置、集成验证和最终包装配，不调用 `build_all_debs.sh all`，不重新编译已迁移模块；如系统仍需要 SimOS base SDK，则只消费单独版本化的 SDK artifact；
- 最终 resident/deb/镜像包内嵌 integration manifest；
- `publish_nextcloud`、`publish_deb_nextcloud` 和 OTA Job 只依赖最终 integration artifact；
- MR/candidate/正式发布使用独立 Registry namespace 和云端目录。

#### 阶段 4 退出条件

- 所有模块有自己的 Required MR pipeline；
- SimOS 集成 Job 不再从源码重新编译已迁移模块；
- 同一组 SHA 在至少两个独立 Runner 上可复现；
- 新增模块必须提交模块 manifest、资源预算和集成测试；
- 旧整包路径只剩本地兼容/应急用途，不再被正式 CI 调用。

### 阶段 5：正式发布切换和旧路径下线（P0）

#### 步骤 5.1：冻结正式输入

正式 Tag 前生成 approved integration manifest，内容包括 SimOS SHA、全部模块 SHA、SDK SHA、配置 SHA、artifact digest、测试结果和审批记录。Tag pipeline 只消费该 manifest，不重新按分支头解析模块。

#### 步骤 5.2：切换发布依赖

将现有 `publish_nextcloud`、`publish_deb_nextcloud`、OTA Job 的依赖从旧 `resident_package/deb_package` 改为最终 integration Job。发布 Job 不得绕过 integration test 直接下载某个模块包。

#### 步骤 5.3：保留可回退路径

至少保留一个最近成功的 approved manifest、对应的全部模块 artifact、SDK artifact 和 SimOS Tag。回滚通过重新装配旧 manifest 完成，不依赖删除后重新构建的分支。

#### 步骤 5.4：下线旧路径

满足以下条件后再下线：

- 新链路连续完成至少一个正式版本和一次回滚演练；
- 新旧最终包已完成差异审计；
- 旧 Registry 包和云端目录没有未完成发布任务；
- `build_all_debs.sh all` 已从正式 `.gitlab-ci.yml` 中移除或显式标记为 manual emergency job；
- 文档写明旧入口的 owner、保留期限和删除日期。

### 阶段 6：稳定性、回滚和持续治理（P2）

- 每周统计 MR 编译成功率、平均等待时间、模块/集成耗时、Runner 峰值资源、缓存命中率和 artifact 存储量；
- 每月做一次 artifact 缺失、校验和错误、SDK 不匹配、Job Token 失效、Runner 中断、重复触发和回滚演练；
- 对每个模块设置包保留期限、candidate 清理规则和正式包不可变规则；
- 新增模块必须同时提交 CI 模板、`debian/control` 依赖、manifest schema、SBOM、资源预算、smoke test 和联合修改说明；
- 对跨项目状态回写、Token、Registry 下载权限和生产变量做季度审计。

## 7. 必须提前解决的问题清单

### P0：不解决就不能切换

- **MR 门禁落点：** 每个子库和 SimOS 主库的 Required job 名称、目标分支、merge train/merged results 策略和绕过权限。
- **构建输入边界：** SimOS 主包、基础 SDK、模块 deb、配置仓库和消息/公共库的归属必须明确。
- **独立 workspace：** 不能继续共享根目录 `build/devel/install`；需要定义每个 Job 的 checkout、缓存和清理策略。
- **SDK/ABI 契约：** 模块声明需要的 SimOS SDK 版本、公共消息版本、编译器/ROS 版本和 ABI 兼容范围。
- **artifact 不可变性：** Registry 路径、版本规则、SHA/校验和校验、跨项目下载权限和过期策略。
- **发布隔离：** MR/candidate/正式 channel、云盘目录、OTA 环境和 CI 凭据必须隔离。

### P1：试点阶段必须解决

- `debian/rules` 中的 `PROJECT_ROOT`、`CMAKE_PREFIX_PATH`、`/work/share/project/resident` 和 `CATKIN_IGNORE` 机制改造。
- 五个模块的实际构建依赖和 Debian `Depends/Build-Depends` 校准，特别是 perception 当前依赖声明与其他模块不一致的问题。
- `config`、`costmap_node` 是否作为独立包；若不是，必须从 `.gitmodules`/构建图中说明其集成角色。
- 两个配置矩阵是否都需要每个模块构建；配置不适用时的声明、跳过规则和集成覆盖率。
- ARM 交叉编译 sysroot、ROS Noetic、GPU/特殊硬件依赖在模块 Runner 中的可获得性和可复现性。
- 包安装 smoke test、ABI 检查、消息兼容性检查和跨模块最小启动测试。

### P2：规模化前解决

- Runner CPU/内存/磁盘容量、模块并发上限、`resource_group`/队列优先级和 cache 污染控制。
- 旧包与新包并行期间的命名冲突、版本回退、Registry 清理和灾备。
- 多模块同时变更时的集成 manifest 生成、下游触发去重和状态回传竞态。
- SBOM、漏洞扫描、构建 provenance、最小权限 Token 和敏感变量审计。
- 日志脱敏、失败重试上限、人工重试入口和可审计的发布/回滚记录。

## 8. 验证矩阵

| 场景 | 预期结果 |
| --- | --- |
| 子库普通 MR 编译成功 | Required job 成功，生成绑定 SHA 的临时 artifact，不能触发正式发布 |
| 子库编译失败 | MR 不能合入，日志和失败 manifest 可下载，修复新 commit 后旧状态不覆盖新状态 |
| SimOS MR 只改集成代码 | 下载固定模块 artifact，完成集成编译/测试，不能重新编译模块源码 |
| 模块 MR 改公共 API | 触发对应 SimOS 集成验证；兼容性失败时子库/集成门禁均失败 |
| artifact 被替换或校验和错误 | 集成在安装前失败，不产生最终包 |
| 某一配置不适用 | 只有在 manifest 明确声明并有规则覆盖时才允许跳过，否则失败 |
| Tag 正式发布 | 仅消费批准的 integration manifest，发布 Job 全部成功后才能上传云盘/OTA |
| Runner 中断/重复触发 | Job 可安全重试，不产生重复正式版本或半成品目录 |
| 回滚 | 使用上一个已验证 manifest 重新装配，不依赖可变分支头 |

## 9. 建议的首批变更清单

1. 在 SimOS 和一个试点子库创建 MR-only 的 `compile/package-smoke` Job，先不改变正式 Tag pipeline。
2. 抽取并测试共享的鉴权、镜像、配置矩阵、artifact manifest 和 checksum 逻辑。
3. 为 SimOS base SDK 建立 candidate Registry 包和下载校验脚本。
4. 改造试点模块 `debian/rules`，使其在删除其他模块源码后仍能编译并生成单模块 deb。
5. 建立 `module artifact -> SimOS integration` 的最小跨项目 pipeline，验证精确 SHA、权限和状态回传。
6. 用一组固定版本同时跑旧整包路径和新模块路径，保存差异报告后再扩大到其他子库。
7. 在 GitLab 设置中启用 Required pipeline，并用一条失败 MR 验证确实无法合入。

## 10. 关键判断

这次改造不应被处理成“给现有 `build_all_debs.sh` 增加几个并行 Job”。现脚本可以复用编译命令、环境准备和单模块入口，但真正的目标是把**源码耦合的串行整包构建**改成**基于不可变模块 artifact 的构建图**。MR 门禁、独立 workspace、SDK/ABI 契约、manifest 和发布隔离是同一个闭环中的必要条件；缺少其中任何一项，都只能得到“看起来并行”，而不能得到可追溯、可复现、可阻断合入的 CI。
