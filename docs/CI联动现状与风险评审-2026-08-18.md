# Workbench 与 SimOS CI 联动现状与风险评审

> 审阅日期：2026-08-18
>
> 审阅范围：`gitops-workbench` 的 Web/API、任务状态、仓库配置和部署配置；`simos` 的 `.gitlab-ci.yml`、resident/deb 构建及发布脚本。
> 结论性质：基于当前工作区代码的静态审阅，不代表线上 GitLab 保护规则、Runner 配置、Nextcloud 发布器或外部 OSS 的实际配置已被验证。

## 1. 结论摘要

现有方案已经能够完成“Workbench 生成跨仓库 Tag → SimOS Tag Pipeline 编译 resident/deb → GitLab Package Registry/Nextcloud 发布 → Workbench 查询部分状态”的主链路，也已加入 Feature 测试包、版本 MR 自动合并重试、配置矩阵和本地模拟模式。

但系统尚未形成完整的发布域模型。当前以**同一种 Tag 驱动**测试包和正式包，以**同一套构建/发布 Job 和目录规则**处理两者；Workbench 以单进程内存锁和本地 JSON 记录状态；跨仓库写入、临时构建分支、Tag、包仓库和云端目录之间没有统一的事务、补偿、保留期和权限策略。因此，所列问题中有一部分已有局部防护，但整体仍存在可见性不够、失败后半成品难追踪、多实例并发失效、权限边界过宽和扩展点位置不清的问题。

建议将 Workbench 明确定位为**发布编排与治理控制面**：负责发布类型、授权、不可变发布计划、幂等键、状态机、跨仓库一致性、产物目录/访问契约、清理计划及扩展插件；SimOS 和各子模块保留**构建执行面**职责，只消费明确的构建上下文并产出统一 manifest。不要把各子模块的编译逻辑继续集中到 SimOS 集成仓库。

## 2. 当前联动链路与边界

```text
用户 / 管理员
  │ Web 登录（仅应用角色）
  ▼
Workbench
  ├─ 读取已启用仓库、分支、Tag
  ├─ 解析各子模块 commit，写 SimOS 的 version.info / software.yaml（正式发版）
  ├─ 创建跨仓库同名 Tag
  └─ 查询 SimOS Tag Pipeline、Job artifact 与本地/云盘元数据
       │
       ▼
SimOS .gitlab-ci.yml（匹配 Tag）
  ├─ resident_package：2 个 config matrix Job
  ├─ deb_package：2 个 config matrix Job
  ├─ 上传 GitLab Generic Package Registry
  └─ publish_*_nextcloud：由 Runner 上的发布器提交到云盘
```

现有 CI 的 Tag 规则同时接受 `V`、`F`、`T` 前缀，未按发布类型拆分 Job；resident/deb 的包仓库名称和云盘目录也未带发布类型。证据见 SimOS [`.gitlab-ci.yml`](../../ubuntu2004/project/simos/.gitlab-ci.yml) 第 29、39-70、84-111 行，以及 [`publish-resident-from-gitlab-package.sh`](../../ubuntu2004/project/simos/ci/resident/publish-resident-from-gitlab-package.sh) 中 `CLOUD_DIR` 的计算。

## 3. 逐项问题、现状与建议

### 3.1 临时包和正式发布包没有完整隔离，发版目录也未隔离

**现状**

- Workbench 已区分入口权限：`user` 只能创建 Feature 包，`admin` 才可通用建 Tag；Feature 包强制 `T` 前缀，并在 SimOS 创建 `automation/feature-package/...` 临时构建分支，不会更新原 Feature 分支。见 [`webapp/auth.py`](../webapp/auth.py) 第 19-31 行、[`webapp/server.py`](../webapp/server.py) 第 1409-1609 行。
- 但 SimOS 的 Tag 正则接受任意来源名以及 `V/F/T` 前缀；`resident_package`、`deb_package`、两个 Nextcloud 发布 Job 都会执行。CI 未根据 `T` 与正式 `V` 选择不同 Job、Runner、Package Registry、云盘根目录或保留期。见 SimOS [`.gitlab-ci.yml`](../../ubuntu2004/project/simos/.gitlab-ci.yml) 第 26-121 行。
- 云盘路径仅包含日期、版本号、类别和产物类型，例如 `/public/Versions/<date>_<version>/<category>/resident`。T 包与正式包若类别相同，逻辑上仍处于同一“版本发布”树；GitLab Generic Package Registry 也仅按 `<package-name>/<tag>` 分组，未声明 release channel。见 SimOS [`publish-resident-from-gitlab-package.sh`](../../ubuntu2004/project/simos/ci/resident/publish-resident-from-gitlab-package.sh) 和 [`publish-debs-from-gitlab-package.sh`](../../ubuntu2004/project/simos/ci/deb/publish-debs-from-gitlab-package.sh) 的 `CLOUD_DIR` 计算。

**风险**：测试包可能被误当正式包下载、被正式发布器同步或进入同一保留/清理规则；仅凭 Tag 前缀和人工识别无法构成发布隔离。

**建议**：为 `feature_test`、`candidate`、`formal_release` 建立显式 `release_channel`，由 Workbench 写入不可变 manifest 和 CI variables；CI 按 channel 路由到不同 Package Registry 名称、云盘根目录、发布器凭据、访问权限和保留策略。正式发布必须是批准后的独立状态迁移，而非“另一种名称的 Tag”。

### 3.2 恢复与重试机制只有局部实现

**现状**

- Workbench 对正式发版的“版本信息 MR 自动合并”有状态、轮询和最多 6 次重试，重试间隔 10 秒；运行记录写入 JSON 并采用临时文件 `os.replace`。见 [`webapp/server.py`](../webapp/server.py) 第 116-133、813-855、977-1065、3131-3161 行。
- SimOS 上传/下载 Package Registry 的 `curl` 有 5 次重试；CI Job 本身没有 GitLab `retry:` 策略，也没有对编译、云盘发布、Tag 创建和跨仓库写入的统一重试。见 SimOS [`publish-debs-to-gitlab-package.sh`](../../ubuntu2004/project/simos/ci/deb/publish-debs-to-gitlab-package.sh) 的 `curl_with_retry`。
- Feature 包执行过程中一旦任一仓库建 Tag 失败，只返回失败结果，不记录可继续执行的持久化 saga，也没有根据已成功写入的 Tag 做幂等恢复。见 [`webapp/server.py`](../webapp/server.py) 第 1549-1609 行。

**风险**：网络抖动、发布器暂不可用、Runner 失败或半数仓库 Tag 已创建时，操作员无法可靠判断“重试、继续还是回滚”；直接重试可能产生新 Tag、重复上传或覆盖/混用产物。

**建议**：将每次操作设计为持久化状态机：`planned → validated → refs_written → build_running → artifacts_verified → published → finalized`，每一步记录外部资源 ID、请求幂等键和补偿动作；把 MR 合并重试、CI retry、上传 retry、人工继续/终止统一纳入该状态机。重试应复用同一发布 ID、同一 Tag 和同一组件 SHA，禁止重新分配版本。

### 3.3 Feature 分支的子库回退策略和可见性不足

**现状**

- 对 SimOS 不存在同名 Feature 分支的其他已启用业务仓库，当前规则静默使用配置的回退 ref（默认 `release`）最新 commit，并把 `resolved_ref`、`resolution`、`commit_id` 写入计划。见 [`webapp/server.py`](../webapp/server.py) 第 636-684、686-753 行。
- 这保证了本次 Tag 固化的是明确 SHA，而不是随后的分支头；该能力是已有保护。
- 但“缺失 Feature → 回退 release”是全局默认，未按仓库、模块或 Feature 任务设为显式允许；用户在创建 Feature 包时并没有被强制确认“哪些模块没有该 Feature、将回退到哪个基线”。`common_refs` 只展示全部已启用仓库的交集，不能解释差异。见 [`webapp/server.py`](../webapp/server.py) 第 233-258、636-684 行。

**风险**：一个看似 Feature 包的产物实际混入其他模块的 release 代码；当 release 已推进时，Feature 的集成基线可能超出开发者预期，且审阅者难从页面快速判断。

**建议**：将每个模块策略配置为 `required_same_feature`、`allow_fallback_to_release`、`pinned_baseline` 或 `excluded`。提交前展示差异表（请求分支、解析分支、SHA、回退原因、风险确认），并把操作者确认、基线 Tag/SHA 写入 manifest。正式发版默认禁止未显式批准的回退。

### 3.4 WebApp 用户并发问题

**现状**

- HTTP 服务是 `ThreadingHTTPServer`；Feature 包和 release-run 的关键区使用 `threading.RLock`。见 [`webapp/server.py`](../webapp/server.py) 第 18、118-128、1409-1436 行。
- 锁只在当前 Python 进程有效。生产 Compose 没有副本数、分布式锁或数据库事务；运行状态是容器卷中 JSON 文件。见 [`docker-compose.yml`](../docker-compose.yml) 第 10-25 行、[`webapp/server.py`](../webapp/server.py) 第 3131-3161 行。
- 一般 `run_operation` 对“预检后写入”没有操作锁或版本/CAS 校验；两个管理员可先后通过预检，再争用相同 Tag/分支。跨仓库执行按顺序进行，失败时不会回退之前仓库。见 [`webapp/server.py`](../webapp/server.py) 第 2180-2216 行。

**风险**：多浏览器、多 worker、容器重启或未来水平扩容会导致重复版本、同名 Tag 冲突、覆盖状态文件、并行发版互相干扰。

**建议**：使用持久化数据库，并以 `release_key = channel + source-ref + resolved-SHA-set + version` 建唯一约束；通过数据库/Redis 分布式锁或 GitLab resource lock 串行化“同版本线分配版本与写 Tag”；所有写 API 接受 idempotency key。前端按钮禁用只是体验优化，不是并发控制。

### 3.5 失败恢复和残留清理不完整

**现状**

- Feature 包会创建临时构建分支和跨仓库 Tag；异常路径只返回错误，不删除已创建分支或已创建 Tag。成功后也没有临时构建分支的保留期/清理任务。见 [`webapp/server.py`](../webapp/server.py) 第 1513-1609 行。
- 正式版本更新 MR 创建时保留源分支（GitLab API 参数 `remove_source_branch: false`），仓库客户端亦无删除分支方法。见 [`webapp/gitlab_client.py`](../webapp/gitlab_client.py) 第 182-205 行及 `create_merge_request` 的实现。
- CI 会清理本次 Job 的临时目录或覆写本次 `deb-packages`，并在失败时上传元信息；但无跨 Job、跨 Tag、Package Registry、Nextcloud 的生命周期协调。见 SimOS [`ci-build-debs.sh`](../../ubuntu2004/project/simos/ci/deb/ci-build-debs.sh) 第 1-55、236-252、351-362 行。
- Web 端“删除 Tag”是管理员手工输入的批量删除，未校验 channel、Tag 是否已发布、跨仓库完整性或关联产物，也未清理构建分支、Registry/云盘文件。见 [`webapp/server.py`](../webapp/server.py) 第 1612-1636 行。

**风险**：残留自动分支和半成品 Tag 增加可见性噪音并可能误触发 CI；删除 Tag 后产物仍可存留，或清理部分仓库导致版本图不一致。

**建议**：建立“资源清单（resource inventory）”与保留策略。每个发布记录其临时分支、Tag、pipeline、registry package、云盘目录；失败时进入 `compensation_pending`，由审批后的补偿任务按安全顺序执行；成功后按 channel TTL 清理临时分支和测试产物。禁止把通用的任意 Tag 删除作为日常恢复手段。

### 3.6 禁用仓库并不等于禁止 Tag 写入

**现状**

- `scope=all` 的正式/集成操作会从 `release_repositories()` 取已启用且非 config 的仓库，禁用仓库会被排除。见 [`webapp/server.py`](../webapp/server.py) 第 2214-2225 行。
- 但单仓操作最终调用 `store.get(repo_id)`，没有验证 `repo.enabled`；通用 `create_tag` / `delete_tags` 可指定一个已禁用仓库执行。仓库页面的读取 API 同样可直接访问该 ID。见 [`webapp/server.py`](../webapp/server.py) 第 2218-2246、3319-3392 行，及 [`webapp/repository_store.py`](../webapp/repository_store.py) 第 55-65 行。

**风险**：“禁用”在页面语义上容易被理解为完全冻结，但实际只是不参加全量编排；管理员仍可误向该仓库写 Tag，违反停用/隔离目的。

**建议**：把状态拆分为 `included_in_release`、`read_enabled`、`write_enabled`、`archived`；所有写入口统一拒绝 `write_enabled=false`，仅允许专门的恢复审批解除。对已禁用仓库显示明确的只读/冻结标识，并审计任何例外写入。

### 3.7 默认账户与所有操作共用的 Token

**现状**

- 未设置环境变量时，应用会启用 `admin/admin123` 与 `user/user123`；示例和文档也公开该默认值。见 [`webapp/auth.py`](../webapp/auth.py) 第 19-57 行、[`webapp/.env.example`](../webapp/.env.example) 第 14-18 行。
- Web 登录 token 仅是应用 session；所有 GitLab API 调用使用服务器环境变量中、按仓库配置的 `token_env`，并非当前登录人的 GitLab 身份。见 [`webapp/server.py`](../webapp/server.py) 第 2238-2255、[`webapp/repository_store.py`](../webapp/repository_store.py) 第 22-35 行。
- 因而普通 `user` 触发 Feature 包时，实际创建临时分支、commit、Tag 和 CI 的是部署服务持有的高权限 GitLab Token。文档要求它至少有 API scope 和目标仓库 Maintainer 权限。见 [`webapp/README.md`](../webapp/README.md) 第 73-87 行。

**风险**：应用 RBAC 与 GitLab 实际审计主体脱节；默认口令遗漏会直接暴露高权限服务能力；一个 Token 被多个仓库/流程复用时，最小权限与轮换范围过大。

**建议**：生产启动时强制拒绝默认口令、缺失 session secret 和 placeholder token；采用 SSO/OIDC 或映射到个人 GitLab OAuth/Project Access Token，并记录“请求用户 + 代表服务账户 + 外部资源 ID”。拆分只读、Feature、正式发布、云盘发布 Token，使用短期凭据/Secret Manager，并定期轮换。

### 3.8 界面已有产物状态查询，但未形成可直接访问产物的统一接口

**现状**

- Workbench 提供 `GET /api/resident-packages?tag=...`，可读取本地 `build-info.json`、云盘 manifest，或查询 SimOS GitLab pipeline/job；响应中含 `pipeline_url`、`job_url`、`artifact_url`、`artifact_path`。见 [`webapp/server.py`](../webapp/server.py) 第 261-300、1066-1165、3319-3330 行。
- 前端会展示/尝试打开 `artifact_url`。见 [`webapp/static/app.js`](../webapp/static/app.js) 第 162、237、283 行。
- `artifact_url` 实际是 GitLab API artifact 地址，需要 `PRIVATE-TOKEN` 请求头；浏览器从 Workbench 页面打开该 URL 不会自动携带服务端 token。也没有 Workbench 的鉴权下载代理、一次性签名 URL、统一 manifest 下载接口，更没有 deb/多模块产物的通用访问模型。见 [`webapp/gitlab_client.py`](../webapp/gitlab_client.py) 第 50-96、129-145 行。

**风险**：页面可“看到路径”不等于用户可安全下载；云盘路径、GitLab artifact 与 registry URL 的访问鉴权和有效期不一致，且未来增加模块后 UI/API 无法统一列出完整交付物。

**建议**：定义 `Release Manifest API`：按 release ID/channel 返回经授权的模块、版本、SHA、校验和、状态和下载项。下载由服务端权限检查后 302 到短期预签名 URL，或使用受控流式代理；不要向浏览器泄露长期 PAT。以 manifest 为唯一产物目录索引，覆盖 resident、deb、日志、release note 和未来子模块包。

### 3.9 测试环境隔离仅覆盖 Workbench 模拟，不覆盖真实 SimOS CI 验证

**现状**

- 代码已提供 `GITOPS_MODE=simulation`：使用本地 `SimulatedGitLabClient`、本地状态文件、关闭调度，并挂载独立的 simulation data；文档明确称其不会调用 GitLab 或触发服务器 CI。见 [`docker-compose.simulation.yml`](../docker-compose.simulation.yml) 第 13-27、[`webapp/README.md`](../webapp/README.md) 第 120-141 行。
- 这解决的是 Web 控制面模拟，不能验证真实 SimOS `.gitlab-ci.yml`、runner、submodule 拉取、Package Registry、Nextcloud 发布器和权限。
- 若测试环境改用真实 GitLab 项目/真实 Tag，SimOS CI 只有 Tag 名正则，没有 `environment`、项目/分支隔离、测试 runner、测试 Registry 或测试云盘路由；符合规则的测试 Tag 会进入真实编译与发布脚本。见 SimOS [`.gitlab-ci.yml`](../../ubuntu2004/project/simos/.gitlab-ci.yml) 第 26-121 行。

**风险**：将“模拟模式”误当“端到端测试环境”会遗漏关键故障；反过来在共享真实环境做验证会实际出包并可能污染正式目录。

**建议**：保留本地 simulation 作为控制面单测；另建独立 GitLab group/project、runner tag、Package Registry namespace、Nextcloud/OSS bucket/prefix、Service Account 和网络策略，作为真实 CI sandbox。CI 必须从受保护变量/环境而非 Tag 文本推导环境，正式发布使用独立 approval gate。

### 3.10 当前并行能力与新增子模块的容量边界未显式治理

**现状**

- 单个 Tag pipeline 当前至少有 resident 与 deb 两类 package job，二者分别以 2 个 config matrix 变体并行；发布 job 又在后续 stage 执行。见 SimOS [`.gitlab-ci.yml`](../../ubuntu2004/project/simos/.gitlab-ci.yml) 第 35-111 行。
- deb 脚本还会在一个 Job 内循环多个 config 变体，且每轮删除/重建工作目录下的 `deb_packages`。见 SimOS [`ci-build-debs.sh`](../../ubuntu2004/project/simos/ci/deb/ci-build-debs.sh) 第 236-252、288-362 行。
- CI 未声明 `resource_group`、Job retry、跨 Tag 并发额度或按 release line 的互斥；实际总并发主要由 GitLab Runner 的标签和外部容量决定，代码中无可观测配额。
- Workbench 的仓库配置可动态新增 enabled repository 和 revision bit，但 SimOS CI 的实际编译与产物脚本仍以 resident/deb 集成包为中心，新增子模块是否需要单独编译、测试、包名和发布器并无契约。

**风险**：增加子模块或同时创建多个 Tag 时，Runner/磁盘/Package Registry/发布器可能被放大负载；同一版本线的发布顺序没有保证。

**建议**：先定义容量模型（每个 build profile 的 CPU、内存、磁盘、时长、最大并发）并配置 Runner tags、`resource_group`、队列优先级和 `interruptible` 策略。将模块变成显式 build graph 节点，采用子模块独立 pipeline/artifact，再由集成 pipeline 按 manifest 组合；新增模块必须同时提交其编译能力、产物契约和资源预算。

### 3.11 OSS/云平台上传和其他模块扩展应归入 Workbench 的编排扩展点

**现状**

- 当前大包先由 SimOS Job 上传 GitLab Generic Package Registry；随后 Nextcloud 发布 Job 下载并调用 Runner 本地的 `simos-ci-publish-resident`，并通过 `sudo` 执行。见 SimOS [`publish-resident-from-gitlab-package.sh`](../../ubuntu2004/project/simos/ci/resident/publish-resident-from-gitlab-package.sh) 的 `SERVER_PUBLISHER`、`REGISTRY_BASE` 与 `sudo -n` 调用。
- Workbench 仅计算/展示预期 `cloud_dir` 和读取产物状态，并不拥有上传状态机、云平台凭据、发布重试或多模块上传编排。见 [`webapp/server.py`](../webapp/server.py) 第 721-748、261-300 行。

**判断**：用户提出“扩展功能放入 Workbench”是合理的，但应放入 Workbench 的**发布编排层**，不是把对象存储 SDK 和所有上传 I/O 都塞进 Web 请求线程。

**建议**：在 Workbench 定义发布 Provider 接口（例如 `artifact_registry`、`nextcloud`、`oss`、`cloud_platform`），持久化 provider job 与回调状态；实际上传由独立 worker/CI job 使用最小权限短期凭据执行。SimOS/子模块只上传标准 artifact + manifest 到中间仓库，Workbench 决定该向哪个 provider、哪个 channel、哪个路径发布，并统一记录可访问地址和清理策略。

### 3.12 Tag 清理逻辑，以及 Tag 驱动发布/CI 的合理性

**现状**

- Tag 是当前唯一明确的 SimOS CI 触发入口，Workbench 正式发版和 Feature 包都创建跨仓库同名 Tag；SimOS `.gitlab-ci.yml` 只对匹配 Tag 的 Job 生效。见 [`webapp/server.py`](../webapp/server.py) 第 812-855、1409-1609 行和 SimOS [`.gitlab-ci.yml`](../../ubuntu2004/project/simos/.gitlab-ci.yml) 第 26-31 行。
- Tag 的优点是不可变提交点、天然 GitLab pipeline ref、可将 SimOS 子模块 gitlink 固化到构建输入；对正式发布尤其合适。
- 但当前 Tag 同时承担“触发构建、描述测试/正式语义、跨仓库关联、版本分配、产物命名和清理对象”多种职责。通用 Tag 删除缺乏引用检查和可恢复性，见 [`webapp/server.py`](../webapp/server.py) 第 1612-1636 行。

**判断**：保留“正式发布由不可变 Tag 触发 CI”是合理的；把所有临时测试、重试和跨仓库事务都绑定到永久 Tag 则不充分。

**建议**：

- 正式发布：只允许从已批准、不可变 release manifest 创建受保护的 annotated Tag；Tag 永不自动删除，保留可追溯性。
- 测试构建：使用 `pipeline trigger + immutable SHA manifest` 或专用短期 `test/*` ref/channel；若仍需 Tag，必须标为短期并有 TTL、访问隔离和自动清理前检查。
- 清理：以发布记录为入口，先确认无下游部署/下载引用，再清理临时 ref、测试 Tag、registry/version 与云端前缀；操作写审计日志并支持 dry-run。

### 3.13 最终应由模块独立编译出包，SimOS 只负责子模块集成

**现状**

- 当前 SimOS CI 的职责仍是 resident 与 deb 的实际编译、配置矩阵切换、Package Registry 上传和云盘发布，而不是纯集成。见 SimOS [`.gitlab-ci.yml`](../../ubuntu2004/project/simos/.gitlab-ci.yml) 第 35-111 行及 [`ci-build-debs.sh`](../../ubuntu2004/project/simos/ci/deb/ci-build-debs.sh) 第 288-362 行。
- Workbench 可以动态解析已启用仓库及其 `submodule_path`/revision bit，SimOS 的 `software.yaml` 和 gitlink 能冻结集成版本；这是向“集成仓库”演进的基础。见 [`webapp/repository_store.py`](../webapp/repository_store.py) 第 15-35、636-684 行。
- 但 Workbench 没有模块构建编排接口，SimOS 也未消费各模块的已发布 artifact manifest；当前仍从源码子模块整体构建。

**建议目标架构**

```text
模块仓库
  └─ 在本仓库 CI 编译 / 测试 / 生成模块 artifact + SBOM + manifest
       ↓（不可变 SHA、版本、校验和）
Workbench
  └─ 解析发布计划、校验模块 manifest、授权并编排发布 Provider
       ↓
SimOS 集成仓库
  └─ 固定各模块 SHA / manifest，执行集成测试、装配和最终镜像打包
```

这样 SimOS 不再是所有模块的唯一构建瓶颈；其发布输入可复现，模块可独立扩展、缓存和回滚。需要注意，最终系统镜像/安装包的装配仍可在 SimOS 集成 pipeline 完成，但不能重新承担所有子模块的完整编译责任。

## 4. 建议的优先级与落地顺序

| 优先级 | 先做什么 | 要解决的核心风险 |
| --- | --- | --- |
| P0 | 禁止默认口令生产启动；区分/缩小 Token；禁用仓库统一拒绝写入；建立正式与测试 channel 的目录、Registry、权限隔离 | 高权限误操作、测试污染正式发布 |
| P0 | 为发布创建持久化状态机、幂等键、资源清单和失败补偿；停止把 JSON + 进程锁作为唯一并发控制 | 并发重复、半成品 Tag、无法可靠恢复 |
| P1 | UI/API 展示模块回退差异并要求确认；统一产物 manifest 和安全下载接口 | 集成成分不可见、产物不可可靠访问 |
| P1 | 建立真实 GitLab CI sandbox 与独立 runner/存储/凭据；给 CI 加资源治理和环境路由 | 测试实际出包、容量失控 |
| P1 | 将 Nextcloud/OSS/云平台发布抽象为 Workbench 编排 Provider + 异步 worker | 新云平台和模块扩展只能改 SimOS 脚本 |
| P2 | 推进模块独立 CI、artifact manifest、集成装配图 | SimOS 编译瓶颈和模块扩展成本 |

## 5. 本次审阅中确认已存在的正向能力

为避免把现状全部描述为“未实现”，以下能力已在当前代码中存在：

- Feature 包限制为 `feature/*`，强制 `T` 前缀、全部已启用仓库预检，并通过临时 SimOS 分支固化版本与组件 SHA。
- 正式发版会记录组件解析快照，版本更新 MR 合并期间不会重新按分支头解析组件。
- 版本 MR 有轮询、有限自动重试和人工重试入口；release-run JSON 写入采用原子替换。
- SimOS resident/deb 有 config matrix，Package Registry 的网络上传/下载有 `curl` 重试，失败时会尽力写出元信息 artifact。
- Workbench 有本地 simulation 模式，不会调用真实 GitLab 或触发真实 CI。
- resident 包已有状态查询接口，能返回 pipeline/job 及 artifact 元数据。

这些能力可以作为下一阶段重构的输入；重点是将它们从分散的脚本和 Web 逻辑，收敛为统一、可审计、可恢复的发布契约。
